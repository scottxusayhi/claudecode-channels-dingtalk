# 钉钉连接器长连接"僵死"问题 —— 分析与修复需求

**状态**：待修复
**影响**：机器人静默失联，最长一次持续 **11 天**，期间用户消息全部丢失且无任何告警
**记录日期**：2026-08-25
**分析基线**：`server.ts`（当前主干）

---

## 1. 问题现象

用户在钉钉群 @ 机器人，机器人**完全无响应**——既不回复，也没有"已收到"的表情回应（reaction）。

最近一次实例：2026-08-20 15:58 用户发送消息，机器人无任何反应；钉钉侧显示消息"3 人未读"。直到 2026-08-25 12:09 才恢复正常。

**关键特征**：故障期间进程仍在运行、机器未关机，从外部看"一切正常"，但机器人实际已失去接收消息的能力。运维人员容易误判为"程序崩溃"或"机器断电"。

---

## 2. 时间线（2026-08-13 ~ 08-25）

| 时间（CST） | 事件 |
|---|---|
| 08-13 15:05 | 连接器进程启动（PID 56374） |
| 08-13 16:38 | `debug.log` 最后一条正常记录（成功回复群消息） |
| 08-14 ~ 08-24 | **日志完全空白，11 天零记录**；期间用户消息全部石沉大海 |
| 08-20 15:58 | 用户发送消息 → 无任何反应（本次问题的触发点） |
| 08-25 12:07:54 | 管理员通过屏幕共享远程登录该 Mac |
| 08-25 12:09:13 | **旧进程自行恢复**，正常接收并处理消息 |
| 08-25 12:14:41 | 新会话的连接器进程启动（PID 13077） |

> 注意 12:09 恢复时，新进程（12:14）尚未启动 —— 说明恢复的是**原有的旧进程**，而非新进程接管。

---

## 3. 诊断证据（排除法）

| 假设 | 检查方式 | 结论 |
|---|---|---|
| 机器断电 / 重启 | `uptime` | ❌ 排除。机器连续运行 27 天未重启 |
| 系统休眠导致 | `pmset -g log` 睡眠事件计数、`pmset -g` | ❌ 排除。**期间睡眠事件为 0**，且 `sleep 0`（系统睡眠被 caffeinate 等阻止） |
| 连接器进程崩溃 | `ps -o lstart,etime` | ❌ 排除。**进程存活 11 天 21 小时从未退出** |
| MCP 协议层故障 | `debug.log` 中有无 `INBOUND` | ❌ 排除。若仅 MCP 断开，连接器仍会记录 `INBOUND`；实际连 `INBOUND` 都没有，说明消息根本没到达进程 |

**结论**：进程活着、机器醒着、配置未变，但**与钉钉服务端的 WebSocket 长连接已断开，且长时间未能重连成功**——即"进程活着但聋了"。

### 为什么"管理员一登录就恢复了"

管理员并未做任何修复操作。推断：远程登录动作唤醒了网络层（唤醒显示器、建立屏幕共享连接、网络接口退出空闲省电状态），使得连接器正在进行的重连尝试恰好在该时刻成功。

这也解释了为何故障能持续 11 天：机器长期无人交互、网络接口处于空闲状态时，重连持续失败且无人察觉。

---

## 4. 代码分析

### 4.1 重连逻辑本身是正确的

`server.ts` 的 `streamLoop()`（约 932 行起）实现无误：

- `while (!shuttingDown)` 无限重连循环，**不会放弃重试**
- 指数退避 `backoff = min(backoff * 2, 60_000)`，封顶 60 秒
- 心跳看门狗：`HEARTBEAT_TIMEOUT = 120_000`（2 分钟），超时主动 `ws.close()` 触发重连
- `onclose` / `onerror` 均有处理

**因此本问题不是"重连逻辑缺失"，而是重连长期失败且完全不可见。**

### 4.2 核心缺陷：连接生命周期日志全部写入 stderr，未落盘

所有连接状态事件仅通过 `process.stderr.write()` 输出，**没有写入 `debug.log`**：

| 事件 | 位置（约） | 输出目标 |
|---|---|---|
| `connecting to stream` | 938 | stderr ❌ |
| `stream open` | 944 | stderr ❌ |
| `heartbeat timeout, forcing reconnect` | 950 | stderr ❌ |
| `stream closed (code reason)` | 963 | stderr ❌ |
| `stream error` | 970 | stderr ❌ |
| `stream loop error` | 975 | stderr ❌ |

而业务事件（`INBOUND` / `NOTIFY` / `STDIO_OUT`）使用 `appendFileSync(join(STATE_DIR, 'debug.log'), ...)` 正常落盘。

该连接器作为 MCP 子进程运行时，stderr 通常不被持久化保存 —— **导致故障期间的重连尝试、失败原因、关闭码（close code）全部丢失，事后无法追溯**。这是本次排查最大的障碍，也是问题能潜伏 11 天的直接原因。

全文件共 **28 处** `process.stderr.write`，其中连接生命周期相关的部分需要同步落盘。

### 4.3 次要问题：多进程并存

排查时发现同时存在两个连接器进程（PID 56374 与 13077），均使用同一钉钉机器人凭据连接。可能导致消息投递到任一进程、行为不确定。需要考虑单实例保护（进程已有 PID 文件机制，见 `removePidFile()`，但显然未阻止重复启动）。

---

## 5. 修复需求

### P0 —— 可观测性：连接生命周期日志落盘

将 `streamLoop()` 中所有 `process.stderr.write` 的连接状态事件，**同时写入 `debug.log`**（复用现有 `appendFileSync(join(STATE_DIR, 'debug.log'), ...)` 方式，带 ISO 时间戳）。

必须落盘的事件：
- 开始连接 / 连接成功（含 endpoint）
- 心跳超时触发重连
- 连接关闭（**必须包含 close code 与 reason**，用于区分是钉钉主动断开、网络中断还是鉴权失效）
- 连接错误、`openStreamSession()` 失败原因（**这是判断重连为何持续失败的关键**）
- 每次重连前的退避时长与累计重试次数

> 建议提取统一的 `logLine(msg)` 帮助函数，同时写 stderr 和 debug.log，避免遗漏。

### P1 —— 主动告警：失联要能被发现

当前故障完全静默。需要增加"长时间无消息/连接不健康"的主动告警机制，例如：

- 连接器持续 N 分钟（建议 10~15 分钟）未成功建立连接，或连续重连失败超过 M 次时，通过独立通道告警（如写入显著的告警日志文件、发送系统通知、或调用备用 Webhook）
- 注意：**告警通道不能依赖这条已经断掉的钉钉长连接**（否则无法送达）。可考虑用钉钉自定义机器人 Webhook（HTTP 直发，与 Stream 长连接相互独立）

### P2 —— 自愈能力增强

1. **连接健康度自检**：重连连续失败超过阈值时，尝试完全重建会话（重新获取 access_token 与 endpoint/ticket，而非复用旧凭据），排除 token 过期导致的死循环。
2. **进程守护 / 开机自启**：考虑用 `launchd` 托管连接器，进程异常退出时自动拉起（当前依赖手动或 MCP 宿主启动）。
3. **单实例保护**：修复 PID 文件机制，防止多个连接器进程并存竞争同一机器人凭据。

---

## 6. 验收标准

1. **可追溯**：断开连接后，`debug.log` 中能清楚看到断开时间、close code/reason、每次重连尝试及其失败原因。
2. **可发现**：模拟长时间断网（≥15 分钟），能收到主动告警，而不是静默无声。
3. **可自愈**：网络恢复后连接器能自行恢复，无需人工登录机器或重启进程。
4. **无并发**：重复启动连接器时，第二个实例应被单实例保护拒绝或安全接管，不出现两个进程同时连接同一机器人。

---

## 7. 复现与验证建议

由于原始故障依赖长期空闲的网络环境，难以直接复现，建议用以下方式验证修复效果：

1. 连接器正常运行后，**断开机器网络 20 分钟以上**再恢复。
2. 观察点：
   - `debug.log` 是否完整记录了断开、每次重连尝试与失败原因；
   - 断网期间是否触发了主动告警；
   - 网络恢复后是否**自动**恢复消息接收，无需任何人工干预。
3. 另可通过防火墙规则单独阻断钉钉 Stream 端点，模拟"网络通但服务端不可达"的场景。

## 附：本次排查用到的命令

```bash
# 进程存活时长（判断是否崩溃过）
ps -o pid,lstart,etime,command -p $(pgrep -f "server.ts")

# 机器是否重启过
uptime

# 是否发生过系统睡眠
pmset -g log | grep -icE "Entering Sleep|Wake from"
pmset -g            # 查看 sleep / displaysleep 等策略

# 连接器日志按日统计（定位失联区间）
grep -ao "2026-08-[0-9][0-9]" <state_dir>/debug.log | sort | uniq -c
```

其中 `<state_dir>` 为环境变量 `DINGTALK_STATE_DIR` 指向的目录。
